Descomposición de **US-01** para Sprint Planning.

| ID | Nombre | Descripción | Objetivo | Dependencias |
|----|--------|-------------|----------|--------------|
| **TK-01** | Modelo de dominio `Organization` y `User` | Definir y persistir las entidades `Organization` y `User` con campos mínimos del PRD: `organization_id`, nombre del tenant, estado activo, `user.role` (`ORG_ADMIN`, `RECRUITER`, `HIRING_MANAGER`) y vínculo usuario–organización. | Establecer la base de datos del tenant como unidad de negocio. | — |
| **TK-02** | Integración con IdP externo (autenticación) | Configurar autenticación delegada al IdP gestionado estándar. Tras login, resolver identidad del usuario y su pertenencia a una `Organization`. | Permitir acceso seguro sin auth custom (limitación §3.1). | TK-01 |
| **TK-03** | Middleware de autorización RBAC | Implementar validación de permisos por rol en endpoints de la API: qué puede hacer cada rol sobre recursos del tenant. Roles fijos, sin jerarquías granulares. | Garantizar que cada acción respeta el modelo de permisos del PRD. | TK-01, TK-02 |
| **TK-04** | Aislamiento multi-tenant en capa de acceso a datos | Asegurar que toda consulta y mutación de datos de negocio filtra por `organization_id` del usuario autenticado. Incluir escenario de prueba cross-tenant. | Cumplir criterio transversal §3.0: ningún dato cruza `Organization`. | TK-01, TK-03 |
| **TK-05** | API de gestión de usuarios internos | Exponer endpoints para que el Organization Admin cree o importe usuarios, asigne rol y los vincule al tenant. Validar que solo `ORG_ADMIN` puede ejecutar estas operaciones. | Cubrir el flujo §3.1 paso 1–2: crear/importar usuarios y asignar rol. | TK-01, TK-03, TK-04 |
| **TK-06** | Pantalla de administración de usuarios y roles | UI para que el Organization Admin visualice usuarios del tenant, asigne roles y vea el estado de cada usuario. Formularios de alta/importación. | Entregar la experiencia de administración descrita en US-01. | TK-02, TK-05 |
| **TK-07** | Bloqueo de acceso sin tenant o rol válido | Manejar el caso de usuario autenticado en IdP pero sin `Organization` activa o sin rol asignado: pantalla informativa, sin acceso a funcionalidades de negocio. | Cubrir el caso borde de US-01. | TK-02, TK-03 |
| **TK-08** | Registro inicial de acciones admin en `AuditLog` | Registrar en `AuditLog` las acciones sensibles de administración: alta de usuario, cambio de rol, acceso a configuración del tenant. | Iniciar trazabilidad GDPR-by-design desde la capa admin (§3.0). | TK-05 |
| **TK-09** | Pruebas de aceptación del flujo admin | Validar escenarios Given/When/Then de US-01: asignación de rol, denegación cross-tenant, bloqueo sin rol. | Confirmar que la historia cumple criterios de aceptación antes de cerrar el sprint. | TK-04, TK-05, TK-06, TK-07 |
